### 0.2 The README overstates one thing, and it matters

The committed README says the paper engine simulates fills

> "behind a risk engine that has final authority"

**That is not what the code does.** `engines/risk/` is invoked by exactly one
caller — the autonomous loop. A manual `POST /api/v1/paper/orders` never reaches
it. See §4.2. The guarantee that is actually true is weaker and still strong:
*the phase 6 paper gate has final authority over every paper fill, and the phase
7 risk engine additionally rules on autonomous proposals before they get there.*

This is the only material documentation/reality discrepancy found.

### 4.2 Finding — the risk engine is not on the manual path

Two call sites resolve leverage, with different arguments:

| Caller | `risk_engine_available` | `risk_max_leverage` |
|---|---|---|
| `services/paper.py:315` (manual **and** the loop's final submit) | `False` | `None` |
| `engines/risk/engine.py:295` (loop pre-check only) | `True` | derived |

Consequences:

1. **`POST /paper/orders` never invokes `engines/risk/`.** No cooldown check, no
   ABNORMAL_VOLATILITY check, no derived leverage ceiling. It gets the phase 6
   gate, which is thorough but is a different, smaller set.
2. **The risk engine's leverage verdict never binds a fill.** Even for
   autonomous orders, `services/paper.py` re-resolves with
   `risk_engine_available=False`, so the paper path can only ever approve
   **1x** (domain minimum) or refuse. The risk engine's approved *size* does
   bind (`margin=verdict.approved_margin`); its approved *leverage* does not.
3. This is **conservative, not dangerous** — the effect is that paper can never
   exceed 1x by any route. But the documented claim of universal final authority
   is inaccurate, and if a venue ceiling ever becomes known the two paths would
   diverge silently.

**Not production-ready as documented. Safe as built.**

## 5. Leverage chain — complete trace

```
requested (1–500, clamped)
      ↓
exchange_max_leverage  ──► ALWAYS None
      ↓                     parsing.py:220 hardcodes max_leverage=None
risk_max_leverage      ──► derived, but only on the risk-engine path
      ↓
approved = min(requested, exchange_max, risk_max)   — only if ALL known
      ↓
order sizing uses approved_leverage ONLY (verified: no `* requested_leverage`)
```

### Empirical result — 216 exhaustive combinations

**Zero violations.** `approved` never exceeded `requested`, `exchange_max` or
`risk_max` in any combination.

| Request | Paper path | Risk-engine path (exch_max=125 hypothetical) |
|---|---|---|
| 1x | **1** `APPROVED_AT_DOMAIN_MINIMUM` | **1** |
| 1.0001x | ✗ | ✗ |
| 2x | ✗ `EXCHANGE_MAX_UNKNOWN` | 2 |
| 3x | ✗ | 3 |
| 125x | ✗ | 3 (`REDUCED_TO_RISK_MAX`) |
| 500x | ✗ | 3 (`REDUCED_TO_RISK_MAX`) |

### Answers to your specific questions

- **Implemented:** the full four-field chain, fail-closed on any unknown, with
  distinct reason codes per missing link.
- **Unknown:** `exchange_max_leverage`. Always. No code path populates it.
- **Why >1x fails:** `exchange_max` is `None` → `EXCHANGE_MAX_UNKNOWN`. On the
  paper path, even a known ceiling yields `RISK_ENGINE_UNAVAILABLE`.
- **Binance leverage brackets available?** **No.** `leverageBracket` appears
  nowhere in the codebase. It requires an authenticated endpoint.
- **Credentials required?** Yes, for brackets. None exist anywhere.
- **Is 1x special-cased?** Yes, deliberately — [ADR 0004](adr/0004-leverage-at-the-domain-minimum.md).
  At **exactly** 1, and only when the chain cannot otherwise complete. 1.0001x
  is refused. Justification: every ceiling the domain accepts is ≥1, so
  `min(1, …) = 1` regardless; and 1x borrows nothing.
- **Can it accidentally exceed a known ceiling?** **No** — 216/216 clean, and
  `_validate_ceiling` refuses malformed ceilings rather than clamping.

> **Phase 7 does not unlock 1x–500x live leverage. It unlocks nothing.** Live
> execution does not exist. The maximum approvable leverage anywhere in this
> system today is **1x**, in simulation.

## 6. Phase 8 dependency seam

### Can crash recovery work with order state only in memory?

## **No.**

Not "degraded" — **structurally impossible**, and the reason is a single
sentence: *the thing a recovery pass queries is exactly the thing a restart
destroys.*

```
1. write order record          ← in memory
2. POST to venue               ← crash HERE
3. response                    ← lost
4. restart → repository is empty
   → no client_order_id to query by
   → no record that an order was ever attempted
   → the venue may hold a position nobody will ever ask about
```

The identity is *derivable* (`blake2b(account|intent_key)`), so in principle it
could be recomputed — but only if the **intent** survived, and the intent is in
the same memory. There is nothing to recompute from.

Worse: with an empty store, `unreconciled_orders == 0`, so
`RECONCILIATION_PENDING` does not fire and **trading resumes immediately** on
top of an unknown venue position. The safety mechanism is silently inert exactly
when it is most needed.

### Durable state Phase 8 requires

| State | Why it must survive |
|---|---|
| Order record + intent | The only thing recovery can query by |
| `client_order_id` | The venue's echo key |
| `submitted_at` | Separates "never sent" (settle locally) from "sent, unknown" (do not) |
| `venue_order_id` | Cancel/query after restart |
| State + transition history | Audit of what was believed when |
| Fills | Position reconstruction |
| Discrepancies | Evidence of venue disagreement |
| Reconciliation attempts | A rising count with no resolution is a signal |
| Credentials | Env is acceptable for 8c; DB-encrypted belongs with phase 1 auth |
| Testnet isolation | Separate settings class, adapter, base URL |

### The dependency, stated exactly

```
8c (testnet) ──requires──► 8b (durable orders) ──requires──► Phase 1 (PostgreSQL)
                                                              ──requires──► DATABASE_URL
```

Phase 1's blocker is now **provisioning, not decision**: ADR 0002 is accepted
(hosted free tier); the signup and connection string need you.

**No new ADR is required** for 8b. Two will be needed later:
- **ADR 0005** — amending ADR 0003 when `/testnet` write routes land (8c)
- **ADR 0006** (recommended) — resolving the §4.2 dual-path inconsistency

## 9. Findings summary

### What is genuinely implemented
Foundation · read-only Binance USDT-M market data · bounded scanner with a
published score · 11 hand-verified indicators · one rule-based strategy · a
fail-closed leverage chain · a pessimistic backtester · a paper engine with real
bid/ask fills, fees and PnL · a 16-check risk engine with a derived leverage
ceiling · an autonomous loop that is off by default · an order state machine in
which `UNKNOWN` cannot be guessed (uncommitted).

### What is incomplete
Limit orders · partial fills · continuous (non-poll) position management ·
crash recovery · durable anything · multi-tenancy · SMC · hyperparameter
optimisation · the manual path's risk-engine coverage (§4.2).

### What is blocked
Phase 1 on `DATABASE_URL` provisioning. 8b on phase 1. 8c on 8b + credentials.

### Architectural risks
1. **The dual leverage path (§4.2)** — two resolvers with different arguments.
   Conservative today; a silent divergence the day a ceiling is known. *Fix
   before 8c.*
2. **`RECONCILIATION_PENDING` is inert without durable orders** — an empty store
   means zero unreconciled means no block. *This is the strongest argument for
   8b preceding 8c.*
3. **Tenant isolation is absent, not deferred** — design it into phase 1.
4. **Everything is in-memory** — a restart is total data loss, disclosed
   everywhere but still the defining constraint.
